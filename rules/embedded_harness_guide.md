# 嵌入式工程 AI Harness 指南（泛用方法论）

> **本文不含任何具体项目的事实。** 它是判据，不是模板——告诉你"该怎么决定写什么"，
> 而不是"照着填空"。文中所有例子都已抽象化。
>
> 不要把本文的任何段落直接复制进新项目的规则文件。通用模板混进项目规范是本文
> 第七节列出的失败模式之一。
>
> 适用范围：默认工程里至少有两个独立编译单元（Boot + App，或 MCU + 上位机）。
> 单工程读者可跳过跨端契约相关内容。
>
> 骨架与工具无关。正文只描述**能力需求**（"你需要一个能在编辑后自动执行检查并
> 阻断的机制"），具体工具的实现方式以脚注形式举例，工具换了只需改脚注。

---

## 一、基本理念：harness 有两条腿，嵌入式缺的是第二条

Harness 是模型之外的一切：提示、规则、文档、工具、检查、反馈。它由两部分组成：

- **前馈**——动手前告诉模型该怎么做（规则、规范、架构文档）
- **反馈**——做完之后告诉模型做错了（编译、测试、检查、实机现象）

Web 和后端的人很少需要专门思考第二条腿，因为 `npm test` 就是完整回路。**嵌入式不是。**
编译要专用工具链，运行要目标硬件，验证要串口、示波器、万用表。回路天然是断的。

结果就是：几乎所有嵌入式团队的 harness 都长成了畸形——**前馈做到 90 分，反馈是 0 分**。
规则文件越写越厚，因为那是唯一看得见的抓手。但规则只能让模型**知道**规矩，产生不了
**守规矩**的约束力。

### 决定一条知识该放哪里的唯一判据

> **违反之后，多久、以什么形式暴露？**

| 违反后的暴露方式 | 该怎么处理 | 为什么 |
| --- | --- | --- |
| 编译报错 | 什么都别写 | 编译器已经在说了，重复一遍只是浪费 context |
| 格式不一致 | 交给格式化工具 | 用 prompt 教格式是最贵的做法 |
| 脚本能判定 | 写成检查 + 闸门 | 一次投入，永久生效，且不消耗 context |
| 要跑到实机、要跑三天才炸 | **写进文档** | 这是文字唯一不可替代的场合 |

大多数团队的规则文件里，前三类占了绝大部分篇幅，第四类几乎没有。而第四类恰恰是
嵌入式最富有的矿藏——**物理世界的知识代码里一个字都没有**。

### 反馈的四个层级

```
L0  编译                  主机侧能编的部分
L1  纯逻辑主机测试         协议编解码、状态机判定、校验、换算公式
L2  跨文件契约检查         脚本比对、依赖方向、枚举与实现的一致性
L3  实机                  真正不可替代的部分
```

**核心洞察：L1 的大小是你的架构决定的，不是硬件决定的。**

一段逻辑能不能在主机上跑，取决于它有没有和寄存器纠缠在一起。把"不碰硬件就能算的
东西"从驱动里挤出来，是嵌入式 harness 最重要的一个架构决策。分得越干净，AI 能自我
验证的比例越高，你要人肉 review 的比例越低。

这不只是为了 AI。它本来就是好设计，只是有了 AI 之后收益翻倍。

## 二、四类载体，各自承担回路的哪一环

| 载体 | 何时进 context | 承担 | 谁保证它是对的 |
| --- | --- | --- | --- |
| 常驻规则文件 | 每次会话 | 前馈：不变量、禁区、验证入口 | 人 |
| 目录级规则 | 在该目录工作时 | 前馈：编码约定、分层要求 | 人 |
| 架构 / 模块文档 | 模型判断需要时 | 前馈：设计意图与契约 | 人 |
| 检查与闸门 | 每次编辑后自动 | **反馈**：可判定的约束 | 脚本 |
| 代码本身 | 模型现场读 | 事实：清单、顺序、依赖 | 编译器 |

越往下越可靠，越往上越贵（常驻内容每次会话都在付费，且靠模型自觉遵守）。

> **设计 harness 就是把每条知识尽量往下推。**

一条规则如果能变成检查，就不该留在规则文件里占位置；一份文档如果记录的是代码能
直接读出的事实，就不该存在。

### 前馈与反馈的分工

建立检查之后，对应的规则条目不是一律删掉。两者职责不同：

> **检查告诉模型"你做错了"，规则告诉模型"该怎么做对"。**

- **正确做法显而易见的** → 规则里删掉。报错信息本身已经说明了替代写法。
- **正确做法不显然的** → 规则保留但压缩到几行。例如"这一层不能直接调那一层"，
  报错只说了不许，但"该发事件给上层再由上层路由"这个正确模式必须由规则来教。

## 三、常驻规则文件（AGENTS.md / CLAUDE.md）写什么

这是最贵的一份文件——每次会话都完整加载。判据要最严。

### 准入三问

每写一条之前问：

1. **不写这条，模型会犯什么具体的错？** 说不出具体错误场景就删掉。
2. **编译器、格式化工具或脚本能不能替我说这句话？** 能就交给它们。
3. **它多久变一次？** 每周变的东西不该放常驻文件，放检查或代码断言里。

一条更狠的说法：**每一行都应该能追溯到一次真实的翻车或一个硬约束。**
写不出对应的事故，说明它是想象出来的规则。

### 嵌入式特有的必备内容

以下六类是嵌入式常驻文件的核心价值，也是大多数团队写得最少的部分：

**1. 跨编译单元契约的位置，以及改一端要同步哪几端**

这是嵌入式最高危的区域：改了 App 侧的命令码忘了改 Boot 侧，两个工程各自编译通过，
问题只在整机联调时出现。必须明确写出"这几个文件是成对的"。

**2. 哪些改动主机验证不了，必须上实机**

明确列出来。这不是免责声明，是**告诉模型它的能力边界在哪**，让它主动声明"这部分
我验证不了"，而不是默认宣称完成。

**3. 硬件常量与版本号的唯一真源**

哪个文件是权威。没有这条，模型会在三个地方各改一遍，或者改错地方。

**4. 时序与硬件怪癖**

上电顺序、看门狗喂狗窗口、某器件的写周期、传感器上电稳定时间、DMA 与中断的关系、
某引脚的模式在哪里配置。

**这一类是常驻文件里最值钱、最不可替代的内容。** 因为它们在代码里根本看不出来——
一行 `delay_ms(200)` 到底是硬件要求还是随手写的？模型分辨不了，于是重构时就敢动它。

**5. 异常与掉电恢复的顺序约定**

哪几步的顺序不能调整，以及调整了会怎样。

**6. 禁区与验证入口**

哪些目录是生成物、示例或第三方库，不作为修改目标；主机编译、测试、检查怎么跑。

### 明确不该写的

- 技术栈罗列、目录树、模块清单、页面/任务列表——模型自己看一眼比你的版本新
- 编码风格细节——那是目录级规则或格式化工具的事
- 项目介绍性文字——没有读者，只有成本

### 关于长度

业界经验值是 60 行以内。这个数字本身不重要，重要的是它背后的机制：
**设一个硬上限，逼迫新增时必须删旧的。** 没有上限的常驻文件一定会膨胀，
因为每一条单看都"挺有道理"。

## 四、架构说明文档写什么

### 判据：有没有单一真源 × 变更频率

```
                  有单一真源（代码里就是权威）？
                    是              否
       高    ┌──────────────┬──────────────┐
变更频率      │ ① 不要写      │ ③ 变成断言    │
       低    ├──────────────┼──────────────┤
             │ ② 可脚本生成  │ ④ 文档核心    │
             └──────────────┴──────────────┘
```

- **① 高频 + 有真源**——模块清单、函数列表、任务表、调用链。**一律不写。**
  模型现场读代码比读你三周前的表格准。这是文档漂移的唯一来源。
- **② 低频 + 有真源**——目录结构、分区表。写了便宜，但更该脚本生成。
- **③ 高频 + 无真源**——最危险的一格。文档一定跟不上。出路是把它变成代码里的
  编译期断言或运行时断言，让它跟着代码一起变。
- **④ 低频 + 无真源**——**文档存在的全部理由。**

### ④ 具体是哪四类

**1. 为什么是这个分层**——不是分层长什么样（那能从目录看出来），是为什么这么切、
合并会怎样、当初考虑过的其他切法为什么不行。

**2. 禁止的依赖方向**——并且写明"违反后不会编译报错，但会导致什么"。
只写"禁止下层依赖上层"是不够的，要写清楚违反的后果，否则模型无法判断这条有多硬。

**3. 硬件怪癖与被硬件逼出来的决策**——某个方案不能用是因为电路上少了个元件、
某个寄存器不能用是因为供电悬空。这类知识只能从实机调试中产生，**永远不可能
从代码推导**，也是文档里最经得起时间考验的部分。

**4. 否决过的方案及理由**——"为什么不用 X"和"为什么用 Y"同样重要。
没有它，下一个人（或下一次对话）会重新提出同一个被否决的方案。

### 检验方法

> **把架构文档删掉，模型靠读代码能重建出多少？重建不出来的那部分，才是文档。**

大多数团队的架构文档能被重建出一半以上。那一半是负担，不是资产。

### 不要写"架构维护文档"

一种常见做法是写一份"改动后该怎么更新架构文档"的规范。**这类文档基本注定失效**，
因为它要求模型在任务末尾主动完成一件枯燥的、没有失败信号的事——这是模型最容易
跳过的任务类型。

正确的替代：

1. 结构性内容改脚本生成，生成的东西不需要维护规范
2. 意图性内容天然低频，不需要维护规范
3. 确实需要提醒的，用闸门（检测到某类改动但文档未动就阻断），把"自觉"变成"必须应答"

**一份需要配套"维护规范"的文档，通常说明它装了不该装的东西。**

## 五、模块功能说明文档的基本要素

### 定位：它是契约的单一真源

模块文档和架构文档的判据不同。架构文档问"能不能从代码推导"，模块文档问的是：

> **这份信息有没有单一真源？**

一个命令码、一个帧格式、一段 Flash 布局，确实"能从代码读出来"——但它分散在两三个
独立编译的工程里，任何一处都不是权威。**这时文档本身就是那个真源。**

所以模块文档允许写字节表、协议表、布局表，而架构文档不允许。这不矛盾，判据不同。

### 什么时候该拆出一份模块文档

满足任意一条：

- 该功能的契约跨越两个以上独立编译单元
- 该功能有掉电、超时、异常中断等需要显式定义恢复顺序的状态
- 该功能的实现分散在三个以上模块，任何单个文件都看不到全貌

不满足的功能不要写模块文档，写了就是负担。

### 必备要素

**1. 数据契约**——布局、格式、字节表、编码。写清楚每个字段的含义、取值范围、
无效值。这是文档作为"真源"的核心职责。

**2. 状态与时序**——完整流程按步骤写，标明哪几步的顺序不可调整以及原因。
异步、跨端、涉及掉电的流程尤其需要。

**3. 失败与恢复**——每种失败的判定条件和恢复动作。特别是"部分完成"状态：
写到一半掉电、传输中断、一端重启而另一端没有，分别怎么恢复。

**4. 版本与兼容**——版本号的真源在哪，新旧版本如何共存，不兼容变更怎么处理。

**5. 一致性维护说明**——这份契约在几个地方有拷贝，改了要同步哪些，有没有自动检查。

**6. 实机验证清单（强制）**——见下。

### 实机验证清单是强制要素

每一份模块文档必须有一节，明确列出：

- 本模块哪些行为**主机无法验证**
- 必须在实机上确认什么，怎么确认，预期现象是什么
- 哪些步骤需要人工介入（烧录、接线、触发特定条件）

**这一节不是可选的，也不是"涉及硬件才写"。** 后者听起来合理，但实际会鼓励人把
模块划归为"纯软件"来逃避写这一节。

三个理由：

1. **它是反馈回路主线在模块层面的落点。** 没有它，模块文档退化成普通详细设计。
2. **它逼你想清楚边界。** 写不出这一节，说明你没想清楚哪些能自动验证、哪些不能。
3. **它是模型的能力声明依据。** 模型读到这一节，才知道自己交付时该说"以下部分
   我无法验证"，而不是默认宣称完成。

写法上不要写成"需要充分测试"这种空话。要具体到：接哪个口、发什么、看什么现象、
什么算通过。**这一节的质量决定了它是资产还是摆设。**

## 六、把回路接回来

按投入从小到大：

### 1. 拓扑检查（最高性价比）

一个常见误解是"架构规范太宏观，没法逐次校验"。**恰恰相反——架构规范比编码风格
更容易校验。**

风格规范是逐行的、语义的（"注释要说明设计意图"），只能靠模型判断。
但架构规范是**拓扑的**：谁能引用谁、依赖方向朝哪边。这是图的性质，一条 grep 就够。

值得做成检查的典型拓扑约束：

- 上层目录不得被下层引用（依赖方向）
- 界面层不得直接引用通信、存储、驱动
- 核心数据类型层不得依赖任何上层
- 驱动层不得引用应用层头文件
- 任务注册文件不得包含任务实现
- 裸机工程不得出现 RTOS API
- 应用层不得直接操作寄存器或调用 HAL

这类检查还有个隐藏好处：**假的规则活不下来。** 检查里写的路径必须真实存在，
否则第一次运行就报错。而规则文件里写错的目录结构可以静静躺三年。

### 2. 契约一致性检查

多份物理拷贝的共享定义、跨端的命令码表、枚举与实现的对应关系——这些都是
"改一处忘另一处，编译全过"的高发区，也是脚本最擅长的。

### 3. L1 主机测试：切分三刀

**第一刀：纯函数**——校验、CRC、换算、编解码。输入输出都在内存里，零依赖。
最好测，也最该优先抽出来。

**第二刀：状态机判定与执行分离**——判定函数只接受"当前状态 + 事件 + 数值"，
返回"下一状态 + 应执行的动作"，**自己不碰任何寄存器**；执行留在调用方。
这样状态机在主机上可以穷举所有路径，包括掉电、超时、非法输入这些实机上极难
复现的分支。

**第三刀：硬件边界的契约**——这一刀是防塌的关键。

前两刀常见的失败方式是：逻辑抽出来测通了，实机照样炸。原因是测试里喂的都是正常值，
而真实的驱动在异常时会返回哨兵值、超时值或未初始化数据。

> **主机测试的价值上限，取决于你有没有把硬件的异常行为也建模进去。
> 只喂正常值的测试，测的是你的乐观想象。**

所以驱动接口的**失败返回值和异常取值必须写进类型定义或文档**，主机测试必须覆盖
这些取值。而这些取值只能从实机调试中获得——这就绕回了下一节。

## 七、实机反馈怎么回流

实机是 L3，永远无法自动化。但它可以被**结构化**，让每次上机的收益最大化。

### 1. 把实机现象文本化

"灯不亮"对模型几乎没有价值，一段带时间戳的日志有。

> **在嵌入式里，日志基础设施就是 harness 基础设施。**

日志通道的质量直接决定模型能不能参与调试。新项目第一天就把日志通道建起来，
优先级高于写任何规则。这包括 Boot、异常处理、中断这些"最难调也最需要日志"的地方。

### 2. 关键路径提前埋点

Flash 擦写、电源时序、状态机跳转、通信握手——这些地方出问题时你没法单步调试。

埋点不是调试手段，是**给模型造的传感器**。没有埋点，模型对实机行为完全失明，
只能猜。

### 3. 实机结论必须当场落进文档

这是整条链路里人类唯一不可替代的环节：

> **实机是唯一能产生新硬件知识的地方。**

"某供电引脚悬空所以某方案不可用"、"某总线的引脚模式已在初始化函数内部配置，
不要在别处重复初始化"、"这个器件在忙时返回哨兵值"——这些没有任何工具能推导出来，
只能是人调出来、当场写下来。

**当场**很关键。今天花两小时定位的问题，如果不写进文档，下次模型还会原样犯一遍，
你再花两小时。

建议固化成硬习惯：

> 每次实机调试结束，问一句：**"这次学到的东西，代码里看得出来吗？"
> 看不出来的，立刻写进架构文档的④或模块文档。**

### 4. 完整闭环

```
实机调试 → 发现硬件行为 → 写进文档（④ / 模块文档）
                              ↓
                    成为主机测试的用例（异常取值建模）
                              ↓
                    L1 覆盖范围扩大 → 必须上实机的范围缩小
```

**这条链走通了，你每上一次实机，就永久缩小一次实机的必要范围。**
走不通的话，每次上实机的收益都是一次性的。

## 八、失败模式与减法判据

反例比正例锋利。以下五种是反复出现的：

### 失败模式 1：规则挂在一个未经验证的机制上

写了一堆带条件触发标记的规则文件，但当前工具根本不解析那种标记，所有规则实际
从未被加载过。规则文件越写越厚，效果为零。

**判据：配置任何自动加载机制后，第一件事是验证它真的生效**，而不是假设它生效。
不同工具的约定不通用，别照抄。

### 失败模式 2：通用模板混进项目规范

规则文件里写着模板自带的目录结构、芯片型号、模块名，与真实项目对不上。

后果比"没有规则"更糟：**你以为在给模型约束，实际在给它歧义。** 模型得先判断
哪些条目适用于本项目，判断错了就按错的执行。这也是"规范很厚但拦不住违规"的
常见原因——规范描述的根本不是这个项目。

**判据：规则里出现的每一个路径、文件名、模块名，都必须在本项目中真实存在。**
变成脚本检查后这个问题自动消失。

### 失败模式 3：靠自觉的维护任务

"完成代码后必须检查并更新某文档"——这类规则的成功率天然很低，因为它枯燥、
在任务末尾、且违反后没有任何信号。

**判据：任何要求"做完后回头做某事"的规则，都要么变成闸门，要么放弃。**

### 失败模式 4：多套工作流并行

同时引入多套任务管理 / 规格驱动 / 评审流程，每套都用了一两次就荒废，留下一堆
半成品目录，之后还要花时间辨认哪套是活的。

**判据：一次只上一套，跑满一段真实周期（比如三个月）再考虑第二套。**

### 失败模式 5：手工同步的多份拷贝

同一份内容在两个位置各存一份，靠人记得同步。**任何需要手工同步的东西，最终都会
漂移。** 要么合并，要么加自动检查。

### 什么时候该做减法

harness 是有维护成本的，它会和项目争夺你的时间。

> **如果你花在维护 harness 上的时间超过它省下的时间，就该做减法了。**

具体的减法信号：

- 某份规则文件你自己已经不记得内容了 → 模型也不会真正用它
- 某条规则从写下起没有阻止过任何一次错误 → 删
- 某份文档里的表格与代码对不上 → 不是更新它，是删掉这张表
- 常驻文件超过长度上限 → 必须删够了才能加

**一次健康的 harness 演进，删掉的应该经常多于新增的。**

## 九、新项目的起步顺序

顺序很重要。最常见的错误是**先堆规则，很久以后才想起接闸门**——这会导致大量
规则从未生效过，而你毫不知情。

### 阶段 0：什么都别写

写第一行业务代码之前不要写规则文件。此时你还不知道模型在这个项目上会犯什么错，
写下的一切都是想象。

唯一该做的两件事：

1. 把编译、烧录、测试命令跑通并记下来
2. 把日志通道建起来

### 阶段 1：先接反馈，哪怕很弱

第一份常驻文件只写三件事，十几行足够：

```
## 验证
- 主机编译 / 测试：<命令>
- 必须实机验证的改动：<列出来>

## 禁区
- <生成物、示例工程、第三方库>

## 契约
- <哪些文件必须成对修改>
```

同时接上第一个闸门——哪怕只检查一件事。
**先养成"有闸门"这个习惯，比闸门本身重要。**

### 阶段 2：规则等第一次翻车再写

一条规则的诞生条件必须是：

> 模型犯了一个错 → 你判断这个错会重复发生 → 才写一条

预先写风格规范是最容易做、也最没用的事。

### 阶段 3：文档从实机知识开始长

架构文档不要一上来就写满。它应该从第一次实机调试的产出开始长——
那才是④类内容的真正来源。

### 最小起步清单

```
常驻规则文件        ~15 行：验证命令 + 禁区 + 契约
编辑后检查的闸门     一个分派脚本，先放一个检查
检查脚本            跟着契约走，有一个写一个
目录级规则          空着，等翻车再填
架构 / 模块文档      空着，等实机产生知识再填
日志通道            第一天就通
```

**其余的，等项目告诉你需要什么再加。**

## 十、一页速查

| 问题 | 判据 |
| --- | --- |
| 这条知识放哪？ | 违反后多久、以什么形式暴露？编译器能说的别写，实机才炸的必须写 |
| 常驻文件写什么？ | 说得出具体事故场景的才写；说不出就删 |
| 架构文档写什么？ | 只写"低频 + 无单一真源"：为什么这样分层、禁止的方向、硬件怪癖、否决的方案 |
| 模块文档写什么？ | 契约的单一真源 + 强制的实机验证清单 |
| 规则能不能变成检查？ | 拓扑约束（谁引用谁）几乎都能；语义判断（注释好不好）几乎都不能 |
| 要不要写维护规范？ | 不要。改成脚本生成或闸门 |
| 什么时候该删？ | 从没阻止过错误的规则、与代码对不上的表格、你自己都不记得的文件 |
| 上实机之后做什么？ | 问"这次学到的，代码里看得出来吗"，看不出来的立刻写进文档 |
