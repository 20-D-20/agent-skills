# 用户可见信息与诊断日志规范

## 适用范围

新增或修改任何最终面向普通用户的内容时，必须遵循本规范，包括页面文案、弹窗、
Toast、状态栏、进度提示、确认信息、输入校验和设备屏幕信息。信息来自 UI、业务层、
MCU 或外部设备均不影响本规范的适用性。

开发日志、串口调试信息和诊断工具不属于用户文案，其 API、格式与语言继续遵循
项目自身的代码规范。

## 核心原则：面向用户与面向开发者分流

同一异常应按受众提供两类信息，禁止把底层错误字符串直接传到界面：

| 渠道 | 目的 | 应包含 |
| --- | --- | --- |
| 用户界面 | 帮助用户理解和继续操作 | 用户层结果、影响、可执行的下一步 |
| 诊断日志 | 帮助开发与维护人员定位问题 | 操作、结果、底层原因、状态码和必要上下文 |

```text
底层错误 ──→ 用户可理解的原因 ──→ UI：发生了什么 + 下一步操作
       └──────────────────────→ Log：完整诊断上下文
```

## 强制规则

### 1. 只展示用户需要理解的信息

- 使用目标用户熟悉的产品语言；必要的产品术语、标准缩写和单位可以保留。
- 禁止显示用户无法利用的实现细节，例如模块名、函数名、协议帧、寄存器、进程、
  线程、堆栈、内存地址、设备节点、底层状态码及系统完整路径。
- 用户主动选择或需要核对的名称可以显示，例如文件名、设备名、产品型号和版本；
  内部 ID、挂载路径、临时目录等不得显示。
- 密码、Token、密钥、连接字符串及敏感个人信息不得出现在 UI 或日志中；日志确有
  业务需要时必须按项目安全要求脱敏。

判断标准：**这项信息能否帮助普通用户理解状态或完成下一步操作？不能则不要显示。**

### 2. 准确、具体、可行动

- 说明用户层面的结果或当前状态；存在可靠解决办法时，给出可立即执行的下一步。
- 已知原因必须映射为准确的用户层类别，不得把所有问题都写成“操作失败”。
- 不得为了隐藏技术细节而描述错误事实，也不得猜测原因、伪造进度或承诺未经验证
  的恢复办法。
- 未知原因可以使用中性描述，但完整原因和上下文必须进入日志。
- 普通可恢复问题不显示错误编号。仅当用户无法自行恢复且确实需要支持人员介入时，
  才显示稳定、公开、无敏感含义的故障编号；原始错误码只写日志。

### 3. 简短、直接、无责备

- 使用完整而简短的句子，优先表达结果与操作，删除无助于决策的过程描述。
- 使用客观、尊重的语气，不使用“非法操作”“用户错误”“你忘记了”等责备性措辞。
- 避免“未知错误”“参数无效”等含糊表述，以及无意义的道歉、感叹号、表情符号、
  网络用语和开发者缩写。
- 使用产品的目标语言；同一句中不随意混用语言，仅保留目标用户熟悉的标准术语、
  缩写和单位。
- 不以固定字数代替可读性判断。必须在当前目标终端验证文案完整可读、不截断、
  不溢出；不能为了适配空间而把必要信息改成含糊措辞。

### 4. 流程与进度只表达用户任务

- 展示用户能理解的任务、阶段和必要注意事项，不展示线程、服务、协议或文件系统等
  内部执行步骤。
- 只有能从实际工作量可靠计算时才显示百分比；否则使用不确定进度提示。
- 耗时操作应按需说明能否取消、离开或关闭；不得用频繁变化的内部状态干扰用户。

### 5. 选择合适的呈现方式

- 仅在需要用户立即确认、选择，或必须告知阻断性结果时使用模态弹窗。
- 普通成功状态和非阻断信息优先使用页面内状态、Toast 或状态栏。
- 不为每个内部步骤弹窗，不用多个连续弹窗表达一个完整流程。
- 危险操作必须明确具体操作及不可逆后果；按钮优先使用“删除”“重新检测”等具体
  动作，避免能用动作表达时仍使用含糊的“是/否”“确定”。

### 6. 异常使用 UI 与 Log 双通道

- 失败、异常及重试失败必须同时提供用户提示和诊断日志，并尽量在同一业务决策点
  生成，避免两者原因不一致。
- 日志应记录操作、结果、底层原因和定位所需的关键上下文；若 UI 显示公开故障编号，
  日志也必须记录该编号以便关联。
- 正常成功、普通进度和操作引导按诊断价值决定是否记录，避免日志噪声。
- 日志系统故障不得阻止或替代必要的用户提示。
- 日志使用的 API、级别、格式和语言由项目代码规范决定，本规范不绑定技术栈。

## 场景结构

| 场景 | 推荐结构 |
| --- | --- |
| 进行中 | 正在做什么 + 必要的等待或操作限制 |
| 成功 | 已完成什么 + 必要时给出下一步 |
| 可恢复失败 | 准确的问题 + 立即可执行的解决办法 |
| 不可恢复失败 | 当前结果 + 真实的支持路径 + 必要时显示公开故障编号 |
| 危险操作确认 | 将执行的操作 + 不可逆后果 + 具体动作按钮 |
| 输入错误 | 哪项内容不符合要求 + 正确格式、范围或可选值 |

## 正反例

```text
❌ MCU 通信超时，UART3 无响应
✅ 设备通信异常，请重新连接后重试

❌ /mnt/usb/sda1 未挂载
✅ 未检测到 U 盘，请重新插入

❌ 参数无效
✅ 浓度应为 0.01～100.00 mg/L

❌ 正在提交数据库事务
✅ 正在保存记录，请稍候

❌ 是否确定？ [是] [否]
✅ 删除后无法恢复，是否删除这条记录？ [删除] [取消]
```

## 变更范围与验收

- 新增文案和本次任务直接涉及的旧文案必须遵循本规范；不要顺手批量改造无关历史
  文案。整体审计应作为独立任务执行。
- 发现任务范围外存在明显的信息泄露时，应向用户指出，由用户决定是否扩大修改范围。
- 完成任务前必须自检：
  1. 普通用户无需了解实现细节也能看懂；
  2. 状态、影响和下一步准确且可行动；
  3. UI 未泄露内部实现或敏感信息；
  4. 异常具有足够且安全的诊断日志；
  5. 原因、进度和恢复建议真实可信；
  6. 文案和操作名称在目标终端完整、清晰、可用。
