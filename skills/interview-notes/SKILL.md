# 面试视角复盘笔记 (interview-notes)

## 触发条件

**显式命令**：`/interview-notes <模块/功能/文件路径>`

**关键词自动识别**：
- "功能是实现了，但设计思路我没真正学到"
- "把 XX 整理成面试能讲的笔记 / 面试怎么讲这块"
- "以被面试者的视角复盘一下 XX"
- 用户反思自己在 AI 辅助开发里只当了调试者，想把决策权补回来

**与 `logic-extractor` 的分工**：logic-extractor 产出中立的第三人称技术文档（可跨项目复用的决策骨架）；本 skill 产出第一人称答辩稿（面试官会怎么问、我怎么答、追问怎么接）。同一模块两份都要时，先跑 logic-extractor 建事实底稿，再跑本 skill 转答辩视角。

---

## 三条铁律

### 铁律 1：全程第一人称，面试口吻，不是文档口吻

❌ "系统采用双区备份机制以保证升级可靠性。"
✅ "我这里没做 A/B 双分区，因为 STM32F103VC 的 256K Flash 装不下两份 App。所以我换了个思路：用 FRAM 里的升级标志位 + App 区 CRC 校验来兜底——代价是升级失败后必须留在 Boot 里重传，不能秒回滚。"

面试官听的是**你怎么想的**，不是规格书。每段都要能直接念出来。

### 铁律 2：先读代码，禁止凭印象

从用户给的入口点出发，顺着调用链跨文件、跨层、跨工程追踪，直到不再产生新的决策点。涉及跨端协议（如 Linux / MCU App / BootLoader 三端契约）必须把三端都看一遍——面试官最爱问"那另一端怎么配合的"。

追踪范围大时委托 Explore 子代理读代码，自己只做归纳。

### 铁律 3：数字不许编，编了面试当场翻车

升级包大小、传输耗时、Flash 擦写次数、超时阈值、成功率——凡是代码/文档里查得到的，写实际值并标出处；查不到的一律写 `【待实测】`，并汇总到第 7 节。

**宁可空着，不可捏造。** 面试官追问"这个 300ms 怎么测的"而你答不上来，比没有这个数字更糟。

---

## 选题：面试官会问什么

扫代码时，专挑**存在"本可以不这样"的地方**——那里才有决策。没得选的地方（HAL 库固定调用顺序、编译器要求）不是决策点，不要凑数。

| 决策类别 | 典型提问 |
| --- | --- |
| 方案选型 | 为什么用这个协议/分区方案/数据结构，而不是那个更常见的？ |
| 边界与失败 | 中途掉电/断线/超时/重复触发会怎样？怎么恢复？ |
| 魔数由来 | 这个超时值、重试次数、缓冲区大小怎么定的？ |
| 跨端契约 | 改这一端，另外几端哪些文件必须跟着改？不改会怎样？ |
| 资源约束 | RAM/Flash/带宽卡在哪，因此被迫放弃了什么？ |
| 可测性 | 这段逻辑你怎么验证的？实机之外能不能测？ |
| 演进 | 需求量翻十倍/多加一种设备，这个设计哪里先崩？ |

每个决策点必须答满三层：**做了什么 → 为什么这样 → 备选方案为什么被否决**。第三层是面试区分度所在。

---

## 薄弱区自查（本 skill 的核心价值）

AI 辅助开发里有大量决策是 AI 替用户做的，用户只验证了结果。**如实标出来**，不要把这些包装成用户的设计。

判定标准：从代码 + 提交记录 + 项目文档里推得出明确工程动机的，算已掌握；推不出、或者只能给"通常这样写"这种泛泛解释的，进第 7 节薄弱区。

对薄弱区给出补课动作，而不是只列问题：该读哪个 datasheet 章节、该做哪个对照实验、该量哪个数。

## 保存位置

默认 `~/.claude/interview-notes/{领域} - {主题}.md`，领域取通用技术类别（如"STM32 固件升级"、"Qt 上位机"），不写具体项目名——将来换公司讲同一个技术点还能用。

保存前检查同名文件：已存在则询问更新还是新建。

## 自检清单

- [ ] 全文第一人称，每段都能直接念出口，没有规格书腔
- [ ] 每个决策点都答满了"做了什么 / 为什么 / 备选为什么否决"三层
- [ ] 没有任何编造的数字；查不到的都写了【待实测】并进了第 7 节
- [ ] 跨端契约类模块，三端都实际读过代码，不是只看了一端推测另两端
- [ ] 第 7 节诚实列出了 AI 替我做的、我讲不出理由的决策，且每条都有补课动作
- [ ] 第 6 节说得出自己方案的边界和代价，不是"暂时没想到"
- [ ] 决策点都是真有得选的地方，没有拿 HAL 固定调用顺序这类无选择项凑数
